# План элемента учёта потребления ресурсов

Контекст для продолжения в другой сессии. Дата: 2026-10-22.
Реализация ещё не начата. Имя элемента и репозитория не выбрано;
`metering` используется только как обозначение ответственности.

## Задача и принятые ограничения

Новый элемент должен собирать статистику CPU, RAM и других ресурсов пользователей
в их реалмах из VictoriaMetrics элемента observability, хранить историю,
предоставлять данные для UI и передавать потребление для списания денег.

- Биллинг уже находится в `exordos_ecosystem`.
- Для хранения потребления выбран PostgreSQL: отдельная БД, миграции и пользователь;
  отдельный сервер PostgreSQL для этого не обязателен.
- Публичные проекты не внедряем, используем их архитектурные идеи.
- Тарифы, расчёт стоимости, финансовые операции и баланс остаются в ecosystem.
- На старте предлагаются API и worker как отдельные процессы одного элемента,
  без Kafka, ClickHouse и TimescaleDB. Это предложение, а не реализованное решение.
- Выделенные ресурсы и фактическая загрузка — разные показатели.
  Какие из них оплачивать, пользователь пока не определил.

## Предлагаемая архитектура

```text
VictoriaMetrics + принадлежность ресурсов из Core / ecosystem
    → сбор и расчёт временных интервалов
    → PostgreSQL: потребление, история принадлежности, прогресс, outbox
        → API статистики → UI
        → доставка подтверждённого потребления → ecosystem
            → тариф → начисление → баланс
```

Собирать завершённые окна с задержкой на поступление метрик.
Начальная гипотеза: worker запускается раз в минуту, окна по пять минут,
задержка в несколько минут. Значения нужно проверить по реальному scrape и нагрузке.
Запрашивать набор ресурсов, а не делать HTTP-запрос для каждой VM.

Для выделенных ресурсов интегрировать размер по времени с учётом изменений:
4 vCPU за 300 секунд дают 1200 vCPU·секунд;
8 GiB RAM за 300 секунд дают 2400 GiB·секунд.
Простая сумма отсчётов не равна интегралу при нерегулярном scrape.
Не продолжать последнее значение бесконечно после исчезновения серии.
Проверить staleness, lookback, границы окон и моменты изменения состояния.

Прогресс хранить по источнику и реалму. Повторять неудачные запросы,
догружать историю в пределах retention VictoriaMetrics. Пропуск не означает ноль.
Недавние неполные интервалы перепроверять; в биллинг отдавать подтверждённые.

## Связь ресурсов и плательщиков

Потребитель ресурса, пользователь с доступом к UI и плательщик — разные сущности.
IAM определяет доступ пользователя к статистике. Ecosystem определяет аккаунт оплаты.

Для управляемых реалмов на проверенном стенде подходит цепочка:

```text
метрика.node_uuid
    → ecosystem.realms.node_uuid
    → realms.project_id
    → billing_projects.account
    → billing_accounts
```

У аккаунта есть `organization_id`; один аккаунт может оплачивать несколько проектов.
Не считать автоматически плательщиком создателя ресурса или реалма.
Принадлежность хранить с периодом действия. Текущая привязка не доказывает прошлую.
При смене принадлежности внутри окна разделять интервал.
Неопределённого плательщика сохранять как нерешённую привязку, не списывать деньги.

Идентифицировать ресурс парой источник/Core + UUID ресурса.
Для нескольких Core нужен стабильный идентификатор источника и контекст реалма.
Не использовать hostname, IP или название как постоянный ключ.

## Хранение и доставка

Предлагаемые группы таблиц:

| Данные | Назначение |
| --- | --- |
| История принадлежности | Ресурс, источник, реалм, проект и привязка к плательщику с периодами действия |
| Интервальное потребление | Ресурс, показатель, период UTC, количество, единица, полнота, версия расчёта |
| Прогресс обработки | Обработанные окна, пропуски и состояние повторного сбора |
| Outbox | Подтверждённые записи, ожидающие передачи в ecosystem |

Объёмы хранить в согласованных базовых единицах с фиксированной точностью,
например vCPU·секунды и byte·секунды; часы и GiB получать преобразованием.
Точную схему, точность и ключи ещё спроектировать.

Уникальность логического интервала должна исключать двойной учёт.
Версия расчёта и ревизия не должны позволять повторно начислить тот же объём.
Интервал, прогресс и задание outbox сохранять атомарно.
Worker повторяет доставку; ecosystem принимает стабильный ID записи,
защищает начисление уникальным ограничением и выполняет финансовую операцию
в транзакции. Потеря ответа не должна приводить к повторному списанию.

До закрытия интервалы можно пересчитывать. После передачи в биллинг изменения
оформлять отдельной корректировкой со ссылкой на исходную запись.
Тарифы применять по периоду потребления; сохранять применённые условия в ecosystem.
Не считать деньги через float.

Для UI нужны выбор периода, группировка по реалму / проекту / ресурсу,
графики, итоги и полнота данных. Предварительную стоимость и списания различать.
Часовые и дневные итоги первоначально получать из интервалов;
материализацию и партиционирование выбирать по оценке объёма данных.

## Проверка orion.stage

Выполнены только операции чтения. Состояние стенда менялось во время проверки,
поэтому числа ниже — последний снимок, а не постоянные характеристики.

- SSH `orion.stage` ведёт на хост `10.20.0.55`.
- Центральный Core доступен на `10.20.0.2`, ecosystem на `10.20.0.29`.
- VictoriaMetrics: `victoria-storage.local.genesis-core.tech`, `10.20.0.61:8428`.
  Запрос без авторизации возвращает 401. Запросы с сервисной авторизацией успешны.
  Секреты в этот файл не сохранялись.
- На хосте stage vmagent собирает node_exporter каждые 15 секунд;
  `instance` задан hostname. Это не проверка частоты всех источников.
- В VictoriaMetrics на момент запроса было по 51 серии
  `exordos_compute_node_info`, `exordos_compute_node_cores`,
  `exordos_compute_node_ram_bytes`, `exordos_compute_node_disk_bytes`.
  Это не число активных или оплачиваемых VM.
- В `node_info` присутствуют `node_uuid`, `project_id`, `hostname`,
  для нод наборов также `set_uuid`. CPU/RAM/диск можно соединять по UUID ноды.
- Ноды управляемых реалмов в центральном Core имеют общий служебный
  `project_id` (`11111113-bc70-4760-9fbf-9fcfe40da329`).
  Напрямую брать плательщика из этого label нельзя.
- В ecosystem есть `realms.node_uuid`, `realms.project_id`,
  `billing_projects.account`, `billing_accounts.organization_id`.
- Последняя агрегированная проверка: 13 MANAGED ACTIVE, у всех есть `node_uuid`,
  но только у 5 есть привязка проекта к billing account;
  1 MANAGED PROVISIONING с нодой и аккаунтом;
  1085 SELF_REGISTERED ANONYM без ноды и аккаунта.
- Локальные `gcl_sdk_audit_events` в Core и ecosystem пусты.
  Это не доказывает отсутствие истории в центральном audit-сервисе:
  его содержимое и пригодность для восстановления не проверены.
- Покрытие ресурсов внутри пользовательских реалмов, частота их scrape,
  retention, исторические окна и поведение после удаления ещё не проверены.
  Проверенная связь относится к VM, размещающей управляемый реалм.

Доступ к Core и ecosystem работал локальным SSH через `-J orion.stage`.
SSH из самого stage с его ключом к этим VM не сработал.
Для продолжения не выводить конфигурационные секреты и пароли в терминал.

## Архитектурные ориентиры

| Проект | Что заимствуем | Что не переносим на старте |
| --- | --- | --- |
| CloudKitty | Обнаружение scopes, сбор по окнам, прогресс обработки | Собственную тарификацию внутри нового элемента |
| OpenMeter | Различие потребителя и плательщика, явную модель потребления | Kafka и ClickHouse без обоснованной нагрузки |
| Lago | Стабильные ID, повторную доставку, проверяемую цепочку начислений | Вторую систему подписок, платежей и балансов |
| OpenCost | Различие allocation / usage / overhead, исключение двойного учёта | Kubernetes-специфическую модель ресурсов |

Источники сравнения:

- [CloudKitty architecture](https://docs.openstack.org/cloudkitty/latest/admin/architecture.html)
- [CloudKitty Prometheus collector](https://docs.openstack.org/cloudkitty/latest/admin/configuration/collector.html)
- [OpenMeter architecture](https://openmeter.io/docs/open-source/architecture)
- [OpenMeter entities](https://openmeter.io/docs/metering/overview)
- [Lago ingestion](https://getlago.com/platform/usage-metering/ingestion)
- [OpenCost specification](https://opencost.io/docs/specification/)

Гарантии дедупликации сторонних проектов зависят от версии и конфигурации;
не переносить рекламное обещание exactly-once в контракт нашей системы.

## План продолжения и критерии проверки

1. Уточнить объект учёта: VM управляемого реалма, ресурсы внутри него или оба уровня.
   Выбрать оплачиваемые показатели, правила остановленных VM, системных ресурсов
   и начала / окончания начислений. Проверка: таблица правил без двойной оплаты.
2. Завершить read-only исследование stage: метрики внутри реалмов,
   идентификатор источника, scrape, retention, staleness, центральный audit.
   Проверка: прослеживаемая связь от серии до плательщика для примеров обоих уровней.
3. Оценить число ресурсов, срок хранения и рост интервальных записей.
   Спроектировать PostgreSQL, историю привязок и контракт ecosystem.
   Проверка: оценка объёма и примеры идемпотентного приёма и корректировки.
4. Создать элемент после выбора имени: манифест, зависимость observability,
   доступ чтения VictoriaMetrics, БД, API и worker.
   Проверка: установка и доступ к источнику на тестовом стенде.
5. Реализовать сбор CPU/RAM/диска и восстановление после сбоев.
   Проверка: известные размеры за известное время, resize внутри окна,
   пропуски, удаление, перезапуск и повторный сбор без дублей.
6. Реализовать API статистики с серверной проверкой доступа.
   Проверка: изоляция проектов и реалмов, совпадение итогов с интервалами.
7. Реализовать outbox и приём в ecosystem, сначала без реальных списаний.
   Проверка: потерянный ответ, повторная доставка, смена тарифа и корректировки.
8. Добавить UI и предварительную стоимость. После сверки включать реальные списания
   только в рамках отдельно согласованного запуска.

Первый MVP: CPU/RAM/диск, интервальное хранение, история принадлежности,
восстановление сбора и API статистики. Затем UI, предварительные начисления,
и после проверки — реальные списания.
